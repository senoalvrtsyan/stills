# C++ Coding Guidelines

Apply these conventions when writing or modifying C++ code.

## Headers & Namespaces

- Filename prefix with project name: `project_ClassName.h`, `project_Utilities.cpp`
- Use `#pragma once` for include guards
- Close namespaces with comment: `} // namespace foo::bar`
- Nested namespace syntax: `namespace foo::bar`

## Whitespace & Layout

- 4 spaces, no tabs
- Space around binary operators: `x = 1 + y - 2 * z / 3;`
- `!` followed by space: `if (! foo)`
- `~` preceded by space: `x = ~y;`
- No spaces around `++`/`--`: `++i`
- Space after comma: `foo (x, y);`
- Space before parentheses with content: `foo (123);`
- No space before empty parens: `foo();`
- No space before array index: `foo[1]`
- Blank line before `if`/`for`/`while`/`do` when preceded by another statement
- Blank line after `}` unless next line is also `}`
- Pointers/references - space after, not before: `SomeObject* ptr;`
- Never declare multiple pointers in one statement - split onto separate lines
- `const` before type: `const Thing& t;`
- No space between nested braces: `{{ "key", value }}` not `{ {"key", value} }`
- Template params no space: `vector<int>`
- Template declaration with space: `template <typename T>`
- Multi-line expressions continue with operator:

```cpp
auto x = foo + bar
       + baz;
```

- When a function call, definition, or constructor doesn't fit on one line, keep the first argument/parameter on the same line as the opening paren and align subsequent ones to the exact column of the first argument. The alignment column is the character position immediately after `( ` (opening paren + one space). Count carefully -- off-by-one errors are common:

```cpp
// good
auto status = VTCompressionSessionCreate (kCFAllocatorDefault,
                                          config.width,
                                          config.height,
                                          kCMVideoCodecType_H264,
                                          nullptr);

// good - continuation aligned to column of first arg
static void paintPanelBackground (core::Graphics& g, core::Rectangle<float> bounds,
                                  core::Colour fillColour);
//                                ^ same column as 'c' in first arg

// bad - off-by-one (one extra space)
static void paintPanelBackground (core::Graphics& g, core::Rectangle<float> bounds,
                                   core::Colour fillColour);
//                                 ^ misaligned by one space

// bad - all args on new lines after open paren
auto status = VTCompressionSessionCreate (
        kCFAllocatorDefault,
        config.width,
        config.height,
        kCMVideoCodecType_H264,
        nullptr);
```

- When a ternary expression doesn't fit on one line, keep `?` on the same line as the condition and align `:` with `?`:

```cpp
// good
auto newMode = currentMode == BrowserCaptureMode::FullWindow ? BrowserCaptureMode::WebContent
                                                             : BrowserCaptureMode::FullWindow;

// bad
auto newMode = currentMode == BrowserCaptureMode::FullWindow
                     ? BrowserCaptureMode::WebContent
                     : BrowserCaptureMode::FullWindow;
```

## Braces & Control Flow

- Allman brace style (opening brace on new line)
- Omit braces for trivial one-liners
- If any branch needs braces, all branches get braces
- Consecutive similar if-statements can be single-line:

```cpp
if (x == 1) return "one";
if (x == 2) return "two";
```

## Lambdas

```cpp
auto f = [] { return 123; };
auto f = [this, &x] (int z) -> float { return x + z; };
auto f = [] (int x, int y) -> int
{
    // multi-line
};
```

## Comments & Literals

- Prefer `//` over `/* */`, space after: `// comment`
- Multi-line `/* */` comments: align vertically on left (no leading space before `*/`)
- Hex lowercase: `0xabcdef`
- Float literals with digits both sides: `0.0f` not `.0f`

### Comments inside a function body

**The default is no comment.** The code states what it does; a comment exists only to state a *why* the code cannot. Justified only by a trigger from this closed list:

- A workaround for an external bug, quirk, or undocumented API behavior
- A non-obvious invariant or precondition the reader must hold to follow the code
- A subtlety of units, encoding, alignment, or lifetime that the types do not carry
- A deliberate tradeoff - a chosen constant, a slower path taken for a reason
- A reference to the spec, ticket, or formula being implemented

If you cannot name the trigger, delete the comment. Never restate the adjacent expression, never narrate a block (`// loop over the frames`, `// check for null`), and never explain another component's behavior - that belongs where it lives, not here. Never invent a rationale you do not have: leave the space for the author who has the real one.

```cpp
// bad - restates the condition it sits on
if (retryCount > maxRetries)   // too many retries
    return false;

// good - states a why the code cannot
// Source rows can carry alignment padding, so copy row by row to pack the
// destination tight.
for (int y = 0; y < height; ++y)
    std::memcpy (destination + y * destinationStride,
                 source + y * sourceStride,
                 rowBytes);
```

Add these last, with the code finished. A comment written while the code is still in flux records what you meant at the time and survives as narration once the code moves on.

A `//` comment is also the right home for the contract of a non-public helper - a `private` method or a function in a `detail` namespace - since those never take `///` doc comments. Public API doc comments follow the `documentation-guidelines` skill.

## Naming

- Variables/methods: `camelCase`
- Classes: `CamelCase`
- Macros only: `ALL_CAPS_WITH_UNDERSCORES`, prefix with project name
- `#undef` macros after use when possible
- Enum **types** are `CamelCase` (like classes); **enumerators** are `camelCase` (like variables/members), never `ALL_CAPS` or capitalized
- No Hungarian notation, no leading/trailing underscores
- Template params: descriptive names, not single letters
- Prefer explicit, domain-accurate names over abbreviations - a clear name removes the need for an explanatory comment

## Accessors & Queries

- Value getters take a `get` prefix. A method that returns a stored or trivially derived property is `getName()`, never a bare noun `name()`. The prefix marks the call as a cheap read and keeps call sites uniform.
- Mutators take a `set` prefix: `setValue()`, `setBounds()`.
- Boolean queries take `is`/`has`/`can`/`should`, never `get`: `isValid()`, `isEmpty()`, `hasBeenRounded()`. `getIsValid()` is wrong.

```cpp
// bad - bare-noun getters
time.value();
time.timescale();
asset.duration();
asset.trackCount();
asset.track (0);

// good - get prefix
time.getValue();
time.getTimescale();
asset.getDuration();
asset.getTrackCount();
asset.getTrack (0);
```

The `get` prefix does NOT apply to methods that are not property reads:

- Named constructors and factories that return a new instance (usually `static`): `Time::fromSeconds()`, `Time::invalid()`, `makeAsset()`. They build a value, they do not read one.
- Type conversions, which take a `to` prefix: `toString()`, `toDouble()`, `toAVRational()`.
- Standard container/range vocabulary, kept bare so range-`for` and generic code work: `size()`, `begin()`, `end()`, `data()`, `front()`, `back()`, `capacity()`, `at()`, `contains()`, `operator[]`. Use `isEmpty()` for domain types; keep std's `empty()` only for a drop-in standard container.
- Verb-named operations whose result is produced by doing work, not by reading state: `abs()`, `convertToTimescale()`.

Decision rule: if a method only hands back a value the object already holds or trivially derives and mutates nothing, it is a getter - prefix it `get`, or use `is`/`has`/`can`/`should` when it returns a `bool`. Anything that constructs, converts, or performs an action keeps its verb, `to`, or std-style name.

A value expressed in a unit is still a getter, so prefer `getSeconds()` over a bare `seconds()`. Whether such a scalar reads better as a getter (`getSeconds()`) or a conversion (`toSeconds()`) is author discretion - pick one and keep it consistent within the type.

## Types & Const

- Mark methods `const` when possible
- Always `override`, never redundant `virtual`
- Use `noexcept` and `constexpr` where applicable
- Use `[[nodiscard]]` for functions returning important values
- Declare variables at last possible moment
- Explicit null checks: `if (myPointer != nullptr)`
- Use modern casts, `reinterpret_cast` for reinterpreting data
- Prefer `int64_t` over `long long`
- Return temp objects non-const to enable move semantics

## Ownership & Lifetime

- No raw `delete` - use smart pointers
- Avoid `new` - prefer stack allocation
- No `new`/`malloc` for arrays - use containers
- Replace manual C allocators (`malloc`/`free`, custom allocators) with RAII containers and resource-owning types
- Avoid statics/globals
- Zero-init POD structs: `= {};`
- Prefer `std::unique_ptr`
- Scope pointers tightly:

```cpp
if (auto* f = getFoo())
    f->doSomething();
```

## Classes

- Order: public (constructors first), protected, private
- Member variables after method declarations
- Private methods at end
- Single-param constructors: `explicit`
- Use `nullptr`, never `NULL`/`0`/`0L`
- Use `struct` for short inline classes with all-public members
- Inheritance: 1 space before colon, base classes vertically aligned:

```cpp
class Thing : public Foo,
              private Bar
{
```

- Member initializer list colon indented 2 spaces:

```cpp
Thing::Thing()
  : member (42)
{
```

## Strings

- Pass by value if storing/modifying (move semantics)
- Pass as `std::string_view` for read-only access
- Pass as `const std::string&` if you need std::string methods

## Miscellaneous

- Never `else` after `return`
- Pre-increment: `++i` not `i++`
- Use `std::abs`, `std::sqrt` over C equivalents
- Range-based for over raw loops
- Always use namespaces, avoid `using namespace`
- `unsigned int` not `unsigned`
- Exceptions end with period: `throw std::runtime_error ("Failed to open file.");`
- Pass small POD types by value, not reference (enables optimizations)

## Auto Usage

```cpp
auto x = 0.0f;                        // OK - obviously float
auto x = 0.0;                         // OK - obviously double
int x = 0;                            // explicit int, not auto
bool flag = false;                    // explicit bool
auto result = someFunction();         // OK for function returns
for (int i = 0; i < n; ++i)           // explicit loop counter
```

## Documentation

- Prefer `///` for member documentation
- `/** */` acceptable for class-level docs only

```cpp
/// Returns the source range.
const TimeRange& getSource() const noexcept { return source; }

/**
    Represents a time mapping.
*/
class TimeMapping
```

## Build Hygiene

- Maintain a zero-warning build across every compiler in the chain (Clang, MSVC, GCC)
- Treat warnings as errors in CI - a warning on one compiler is a bug waiting to surface on another
- Fix the underlying cause rather than suppressing the warning; suppress only with a justifying comment

## Modern C++ Idioms

- Replace `#define` constants with strongly typed `enum class` or `constexpr` values
- Replace state-mutating preprocessor macros with lambdas capturing local context by reference (`[&]`)
- Replace repetitive bitwise/token macros with variadic templates (`template <typename... Args>`)
- Replace hardcoded static data tables with localized static initializers and `constexpr` routines
- Prefer strong types over loose primitive integers - a class-scoped `enum class` beats a bare `int` or `#define`

## Header-Only Library Design

- Keep the public API surface as minimal as possible
- Aggressively hide internal state, algorithm mechanics, auxiliary constants, and helper structs in private sections to reduce compile-time coupling and misuse
- Design for zero dependencies where practical - a self-contained header is the easiest to adopt
- Group loosely coupled parameters into lightweight value-type structs to prevent parameter bloat

## Refactoring

- Modernize legacy C into idiomatic C++ incrementally, maintaining 100% functional and performance parity at each step
- Systematically reduce variable scope, eliminate mutating global state, and encapsulate scattered flags into cohesive value types
- Identify implicit data/state patterns and extract them into single-responsibility classes
- Guard every refactor with targeted unit tests and micro-benchmarks so behavioral or latency regressions surface immediately
